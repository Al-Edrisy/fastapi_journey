# Reflection: FastAPI + MongoDB Authentication and Domain Migration

## 1. What is an ODM and why do we use Beanie instead of writing raw MongoDB queries?
An ODM (Object Document Mapper) allows us to represent our database documents as Python objects. By using Beanie with FastAPI, we can define our collections as Pydantic-based classes mapping directly to MongoDB documents. Writing raw queries (like with Motor directly) forces us to construct complex dictionaries and doesn't inherently validate the structure of the data or provide autocompletion. Beanie lets us use simple awaitable methods like `find()`, `get()`, and `save()` on standard Python objects. This drastically speeds up development, ensures predictable data types, and makes our code less prone to subtle syntax errors.

## 2. What is the role of the Database class — why wrap Beanie methods inside it instead of calling them directly in routes?
The custom `Database` wrapper serves as an abstraction layer or repository pattern. By wrapping Beanie methods in our `Database` class, we decouple our business logic inside the routes from the specific ODM we’re using. If we wanted to change how `save()` works, or even migrate away from Beanie in the future, we only have to update the logic inside the `Database` class rather than modifying every single route. It also gives us a single place to handle logic like checking if an object exists before attempting to return it or update it.

## 3. What happens if initialize_database() is not called on startup? What would break and why?
If the `@app.on_event("startup")` fails to call `initialize_database()`, the connection between the Beanie document models and the Motor async client will never be established. When a user calls any route that tries to query the database (e.g., `event_database.get_all()`), the route will crash and return an Internal Server Error (500). Beanie models internally depend on having an initialized motor client to execute their base async methods, so it would raise an `InitMongoDB` error or a similar missing client exception.

## 4. What is the difference between the Event document and the EventUpdate model, and why are they two separate classes?
The `Event` document inherits from `beanie.Document` and dictates exactly how an event is structured *inside the database*, including the underlying `_id` field that MongoDB automatically dictates. On the other hand, `EventUpdate` is a pure Pydantic `BaseModel` used strictly for handling API payload validation during `PUT` requests. They are separated because a `PUT` request usually shouldn’t be forced to send every field (hence we use `Optional` in `EventUpdate`), whereas the core `Event` document requires specific data to be present in order to accurately save it into the collection.
